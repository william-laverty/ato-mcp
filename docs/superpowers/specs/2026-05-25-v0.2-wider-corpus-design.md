# ato-pro v0.2 — wider corpus + framework changes

**Date:** 2026-05-25
**Status:** Approved for implementation planning
**Owner:** William Laverty
**Builds on:** [v0.1 scaffolding spec](2026-05-25-ato-pro-mcp-design.md) and [v0.1 plan](../plans/2026-05-25-v0.1-scaffolding.md), both shipped on `main`.

## 1. Goals, non-goals, scope

### Goals

1. **Close the corpus gap with `gunba/ato-mcp`** — add the ATO legal database (rulings, edited PBRs, case summaries) so we cover what they cover.
2. **Go beyond ato-mcp** — add legislation (`legislation.gov.au` XML compilations) and state revenue offices (NSW, VIC, QLD, SA, WA, TAS, ACT, NT). ato-mcp doesn't have either.
3. **Make tax-law currency first-class** — point-in-time queries across `search`, `get_definition`, `get_threshold`. Tax answers depend on what the law said at the relevant date.
4. **Match ato-mcp's tool surface** — `get_definition`, `get_doc`, `get_doc_anchors`, `get_threshold`, structured anchor + citation graph.
5. **Ship as a real release** — `ato-pro-mcp update` with no args fetches the latest published corpus from GitHub, verifies sha256, atomic install. Monthly corpus rebuild via CI cron.
6. **Better retrieval quality** — swap embedding model to Granite Embedding Small R2 (same as ato-mcp).

### Non-goals (v0.2)

- Personal facts layer, web onboarding, hosted backend on Vercel + Supabase (v0.3).
- Hero workflow tools (`deduction_discovery`, `bas_prep_checklist`, `audit_risk_check`, `depreciation_helper`) (v0.4).
- Raw AustLII / Jade bulk scrape. We use `law.ato.gov.au` summaries instead — same publisher as ato.gov.au, same ToS.
- Image data assets (`get_asset` tool from ato-mcp). The existing `fetch` covers the cases that matter.
- Granular cross-jurisdiction harmonisation of state revenue (e.g. mapping "payroll tax" semantics across states). v0.2 ships state revenue as separately-typed docs; the agent reasons about jurisdiction.
- Multi-model embedding indexing.
- Real-time corpus updates. Monthly cron is enough.
- AI-generated tax explanations baked into the MCP — agents do the prose; we do the retrieval and structured data.
- ATO Tax Practitioner Board register or ABR live lookups.

### Success criteria (measurable)

- Corpus reaches ≥ 150,000 docs (parity with ato-mcp's ~158k) including PBRs.
- Hand-curated 50-question eval `recall@10 ≥ 0.90` and `MRR ≥ 0.7` against expected `doc_id` citations.
- Point-in-time queries return different chunks for FY24 vs FY18 questions where the law actually changed.
- `update` with no args downloads, verifies, and installs a fresh corpus from GitHub releases without manual intervention.
- All v0.1 tools still work identically (no regressions).

## 2. Corpus expansion

### 2.1 Legislation (`legislation.gov.au` Federal Register)

The authoritative Australian statute source. Bulk-download XML compilations — each Act has every historical compilation indexed by date.

**Acts to ingest:**

- *Income Tax Assessment Act 1997* (ITAA 1997) — main income tax statute
- *Income Tax Assessment Act 1936* (ITAA 1936) — still partly in force
- *A New Tax System (Goods and Services Tax) Act 1999* — GST Act
- *Fringe Benefits Tax Assessment Act 1986* (FBTAA)
- *Taxation Administration Act 1953* (TAA) — penalties, lodgement obligations
- *Superannuation Industry (Supervision) Act 1993* (SISA)
- *A New Tax System (Australian Business Number) Act 1999* — ABN Act

**Acquisition.** Federal Register publishes per-Act XML bulk downloads at `https://www.legislation.gov.au/Series/<series-id>/Compilations`. Each compilation has a `RegisteredDate` and `EndOfCompilationDate`. Download every compilation back to 2000 (older treated as "historical baseline" for `include_old=true`).

**Chunking.** Acts are structured. Use the XML hierarchy directly — `Chapter > Part > Division > Subdivision > Section > Subsection`. Each Section gets one chunk; long Sections get split at Subsection boundaries. `heading_path` records the full hierarchy.

**doc_id.** `legis:<act-key>/<section-number>` (e.g. `legis:itaa1997/8-1`). Anchors point to subsections (`#1-a-i`).

**Effective dates.** Chunk inherits the compilation's date range. When a section was amended, both pre- and post-amendment chunks exist with non-overlapping ranges.

### 2.2 ATO legal database (`law.ato.gov.au`)

This is what makes ato-mcp 7× bigger than us. Three sub-collections:

**Public rulings** — TR (Taxation Ruling), TD (Tax Determination), GSTR (GST Ruling), GSTD (GST Determination), PR (Product Ruling), CR (Class Ruling), LCR (Law Companion Ruling), PCG (Practical Compliance Guideline), MT (Miscellaneous Tax Ruling), FTR (Fuel Tax Ruling). Each ruling has a stable ID like `TR 2024/5`.

**Edited Private Binding Rulings (PBRs)** — taxpayer-specific rulings, edited to remove identifying details, published as guidance for similar fact patterns. Massive corpus — tens of thousands. ID format like `1051234567890`.

**Case decisions and summaries** — ATO-curated summaries of AAT/ART/Federal Court tax decisions, with citations and links to AustLII/Jade. We ingest the ATO summary + metadata, not the raw decision text.

**Acquisition.** `law.ato.gov.au` has an XML sitemap (verify in plan week 1 — see open question §5.2.3); each ruling has a structured URL `https://www.ato.gov.au/law/view.htm?docid=<type>/<id>/<part>`. If the sitemap is unavailable or incomplete, fallback is paginated search-result crawling per type.

**doc_id.** `ato-law:<type>/<id>` (e.g. `ato-law:TR/2024/5`, `ato-law:PBR/1051234567890`).

**doc_type.** As enumerated in §3.1 — `ATO_RULING_TR`, `ATO_RULING_TD`, …, `ATO_PBR`, `ATO_CASE_SUMMARY`.

**Effective dates.** Rulings explicitly state "Date of Effect" — parsed into `effective_from`. Withdrawal dates parsed into `effective_to`. PBRs have an "Issue Date" and apply only to the specific taxpayer/year stated; we record both.

**Volume estimate.** ~5k public rulings + ~120k edited PBRs + ~10k case summaries = ~135k new docs. Combined with the existing 22k ato.gov.au, this puts us at ~157k docs — parity with ato-mcp.

### 2.3 State revenue offices (8 jurisdictions)

Each state/territory publishes its own tax content. Topic coverage varies but the common pieces are payroll tax, land tax, stamp duty (transfer/conveyance duty), motor vehicle duty, and gambling taxes.

**Sites:**

- NSW Revenue — `revenue.nsw.gov.au`
- State Revenue Office Victoria — `sro.vic.gov.au`
- Queensland Revenue Office — `qro.qld.gov.au`
- RevenueSA — `revenuesa.sa.gov.au`
- WA Department of Finance — `wa.gov.au/organisation/department-of-finance/state-revenue`
- State Revenue Office Tasmania — `sro.tas.gov.au`
- ACT Revenue Office — `revenue.act.gov.au`
- Northern Territory Revenue — `treasury.nt.gov.au/dtf/territory-revenue-office`

**Acquisition.** Sitemap-driven where available, BFS-from-seed where not. Per-jurisdiction scraper module so site-specific quirks stay isolated. Strict rate-limit per host (0.5 s per worker, 4 workers max per host).

**doc_id.** `staterev-<juris>:<path>` (e.g. `staterev-nsw:payroll-tax/lodge-and-pay`).

**doc_type.** `STATE_REV_NSW_PAYROLL`, `STATE_REV_NSW_LAND`, `STATE_REV_NSW_DUTY`, … per jurisdiction-tax pair, classified by URL pattern.

**Volume estimate.** ~5–15k pages total across 8 jurisdictions.

### 2.4 Re-indexing existing ato.gov.au content by ruling type

Today every ato.gov.au page is `ATO_GUIDE`. Some are actually rulings hosted on the main site (mostly older content) — re-classify by URL pattern and page metadata so the doc_type taxonomy is consistent.

No re-scrape needed. Pipeline gets a `reclassify_doc_types` step that updates the `doc_type` column based on URL pattern (e.g. `/law/view.htm?docid=TR/...` → `ATO_RULING_TR`).

## 3. Framework changes

### 3.1 Doc-type taxonomy

A typed enum, used in `doc_type` columns and `search`/`get_chunks`/`stats` filters:

- ATO content: `ATO_GUIDE`, `ATO_RULING_TR`, `ATO_RULING_TD`, `ATO_RULING_GSTR`, `ATO_RULING_GSTD`, `ATO_RULING_PR`, `ATO_RULING_CR`, `ATO_RULING_LCR`, `ATO_RULING_PCG`, `ATO_RULING_MT`, `ATO_RULING_FTR`, `ATO_PBR`, `ATO_CASE_SUMMARY`
- Legislation: `LEGISLATION_ITAA1997`, `LEGISLATION_ITAA1936`, `LEGISLATION_GST_ACT`, `LEGISLATION_FBT_ACT`, `LEGISLATION_TAA`, `LEGISLATION_SIS_ACT`, `LEGISLATION_ABN_ACT`
- State revenue: `STATE_REV_<JURIS>_<TAX>` (e.g. `STATE_REV_NSW_PAYROLL`, `STATE_REV_VIC_LAND`, `STATE_REV_QLD_DUTY`)

### 3.2 Point-in-time queries first-class

Every chunk already has `effective_from` and `effective_to` from v0.1 schema. v0.2 actually uses them.

**`search` gains a `pit` parameter** — ISO date `YYYY-MM-DD`. When set, the SQL adds:

```sql
WHERE (effective_from IS NULL OR effective_from <= :pit)
  AND (effective_to   IS NULL OR effective_to   >  :pit)
```

When unset, defaults to today. Pre-2000 non-legislation already excluded unless `include_old=true` (v0.1 schema). The same predicate applies to `get_definition` and `get_threshold`.

**Population by source:**

- Legislation: each compilation's effective range, propagated to its chunks.
- ATO public rulings: `effective_from` from "Date of effect"; `effective_to` from "Withdrawal date" if present.
- PBRs: `effective_from` = issue date; `effective_to` = end of applicable year as stated in the ruling.
- Case summaries: `effective_from` = decision date; `effective_to` = NULL (decisions don't expire).
- ato.gov.au + state revenue: `effective_from` = NULL (treat as current); content typically reflects current law.

**Default `pit` policy**: today's date in the user's local timezone. The agent should pass an explicit `pit` for historical questions; this is documented in the MCP `initialize` instructions surfaced to clients.

### 3.3 New tool: `get_definition`

Statutory definitions, with a labelled ordinary-meaning fallback. Same shape as ato-mcp's tool.

```ts
// input
{
  term: string,
  pit?: string,            // ISO date; default today
  jurisdiction?: string,    // default "AU"
}

// output
{
  term: "trading stock",
  kind: "statutory" | "ordinary",       // agent must respect this
  source?: { doc_id, anchor, citation }, // present iff kind === "statutory"
  body: string,
  effective_from?: string,
  effective_to?: string,
  alternatives?: Array<{ doc_id, citation, body }>  // other Acts that define the same term
}
```

**Population.** Pipeline extracts the Dictionary sections from each Act (e.g. ITAA 1997 s 995-1, GST Act s 195-1) into the `definitions` table (v0.1 schema). One row per `(term, doc_id, effective range)`.

**Fallback.** If no statutory match at the given `pit`, call into Open English WordNet (CC-BY 4.0, downloaded on first use). Result tagged `kind: "ordinary"` so the agent doesn't cite it as statutory. Same approach as ato-mcp.

### 3.4 New tool: `get_doc`

Returns a whole document — cleaned HTML, metadata, all anchors.

```ts
// input
{ doc_id: string, pit?: string }

// output
{
  doc: Doc,
  cleaned_html: string,
  anchors: Array<{ anchor_id, name, chunk_id }>,
  related: Array<{ doc_id, citation, kind: "cites" | "cited_by" | "supersedes" | "superseded_by" | "historical_version" }>
}
```

### 3.5 New tool: `get_doc_anchors`

Lighter than `get_doc` — just the anchor list, citation graph, and historical-version URLs.

```ts
// input
{ doc_id: string }

// output
{
  doc_id,
  anchors: Array<{ anchor_id, name, chunk_id }>,
  inbound_citations: Array<{ from_doc_id, from_chunk_id, citation_kind }>,
  outbound_citations: Array<{ to_doc_id, to_anchor, citation_kind }>,
  historical_versions: Array<{ pit, doc_id, url }>
}
```

### 3.6 New tool: `get_threshold`

Time-keyed scalar lookup. Lets the agent answer "what's the GST registration threshold as of 2025-06-30?" deterministically rather than searching.

```ts
// input
{ name: string, pit?: string }

// output
{
  name: "gst_registration_threshold",
  value: 75000,
  unit: "AUD",
  effective_from: "2007-07-01",
  effective_to: null,
  source: { doc_id, anchor, citation }
}
```

**Initial threshold list (~25 entries) — hand-curated extractors in the pipeline:**

- `gst_registration_threshold`, `gst_registration_threshold_nonprofit`, `gst_registration_threshold_taxi`
- `instant_asset_write_off`, `instant_asset_write_off_threshold`
- `cgt_discount_individual`, `cgt_discount_super`
- `super_guarantee_rate`, `super_concessional_cap`, `super_nonconcessional_cap`
- `medicare_levy_rate`, `medicare_levy_surcharge_threshold_single`, `medicare_levy_surcharge_threshold_family`
- `low_income_threshold`, `tax_free_threshold`
- `payg_instalment_minimum_threshold`
- `fbt_rate`, `fbt_record_keeping_exemption_threshold`
- `div7a_benchmark_interest_rate`
- `r_and_d_offset_rate_aggregated_turnover_threshold`

Each extractor knows its specific source URL and parses the value out deterministically. Tests pin against a known good value for a known date so pipeline regression is caught.

### 3.7 Citation and anchor graph

Pipeline now populates the `citations` and `anchors` tables (v0.1 schema already has them; v0.1 just doesn't fill them).

**Anchor extraction.** Per-document: find every `id="..."` attribute on headings + named sections. Store `(anchor_id, anchor_name, chunk_id)` rows pointing to the chunk that contains that anchor.

**Citation extraction.** Per-chunk text, regex-detect citation patterns:

- "TR 2024/5", "TD 2024/3", "GSTR 2024/1", … (rulings)
- "section 8-1", "s 8-1 ITAA 1997", "subsection 6-5(1)" (legislation)
- "[2024] FCA 100", "[2024] AATA 50" (cases)
- "Division 7A", "Subdivision 152-D" (legislation parts)

Resolve each pattern to a `to_doc_id` + optional `to_anchor`. Unresolved citations become `[fetch:<uri>]` markers in the surfaced text.

### 3.8 Existing tool updates

- `search` — gains `pit`. Otherwise unchanged.
- `get_chunks` — gains `pit` filter; defaults to "don't filter" (different from search) so the agent can always retrieve a specific chunk it already has the ID for.
- `fetch` — supports new URI schemes: `legis:<act-key>/<section>`, `ato-law:<type>/<id>`, `staterev-<juris>:<path>`. Existing `ato:<path>` continues to work.
- `stats` — adds per-source breakdown (docs and chunks by source enum) and per-doc-type counts.

## 4. Release flow, embedding swap, monorepo

### 4.1 Corpus release flow

Replaces v0.1's "build locally, install with a path" with "publish a release, install from GitHub".

**Build artefact** produced by the pipeline:

```
release/
├── ato-corpus-vYYYY.MM.sqlite.zst   # zstd-compressed corpus (level 19)
└── manifest.json                     # release metadata
```

`manifest.json`:

```json
{
  "schema_version": "0.2.0",
  "release_tag": "v0.2.0",
  "generated_at": "2026-06-15T03:14:00Z",
  "embedding_model": "ibm-granite/granite-embedding-small-english-r2",
  "embedding_dim": 384,
  "sources": {
    "ato_website":   { "docs": 22416,  "chunks": 181969, "scraped_at": "..." },
    "legislation":   { "docs":  5400,  "chunks":  41200, "scraped_at": "..." },
    "law_ato":       { "docs": 135000, "chunks": 380000, "scraped_at": "..." },
    "state_revenue": { "docs":  9800,  "chunks":  35400, "scraped_at": "..." }
  },
  "corpus_sha256": "...",
  "compressed_size": 712345678,
  "uncompressed_size": 2345678901
}
```

**CI workflow** at `.github/workflows/corpus-build.yml`:

- Triggers: monthly cron (1st of month, 03:00 UTC); `workflow_dispatch` for manual runs.
- Steps: `uv sync` → `uv run ato-pipeline build` → compress with `zstd -19` → compute sha256 → `gh release create v0.2.YYYY.MM` with the two artefacts.
- Re-runs for the same month replace artefacts on the same release.

**Client-side `update`** (no args):

1. `GET https://api.github.com/repos/<owner>/<repo>/releases/latest` (configurable repo via env var; defaults to the project's own).
2. Pick the asset matching `ato-corpus-v*.sqlite.zst` + the corresponding `manifest.json`.
3. Stream-download both into `<data_dir>/staging/`.
4. Verify `sha256(corpus) == manifest.corpus_sha256`.
5. Decompress staging zst → `<data_dir>/staging/ato.sqlite`.
6. Open the SQLite read-only to verify it parses + has the meta key set.
7. Atomic rename `<data_dir>/staging/ato.sqlite` → `<data_dir>/live/ato.sqlite`.
8. Write `<data_dir>/installed_manifest.json` from the staging manifest.
9. Clean up staging.

**`update <path>`** still works for local installs (development, air-gapped users, custom corpora).

**Mismatch handling:**

- If `installed_manifest.embedding_model` ≠ the model the MCP loads at runtime, refuse to start and explain — vectors won't match.
- If sha256 verify fails, abort install, keep the old corpus, exit non-zero.
- If GitHub API rate-limits (60 req/h unauthenticated), surface a clear error suggesting `GH_TOKEN` env var. The MCP respects `GH_TOKEN` if set but doesn't require it.

### 4.2 Embedding model swap to Granite Small R2

**Pipeline side.** Change `embedding_model` in `PipelineConfig` to `ibm-granite/granite-embedding-small-english-r2`. `Embedder` already uses `sentence-transformers`, which loads Granite the same way.

**MCP runtime side.** `OnnxEmbedder.load()` needs the ONNX-quantised version. `@xenova/transformers` mirrors many HF models under the `Xenova/` namespace. If the Granite ONNX isn't mirrored:

- **Option A** — convert at release time using `optimum-cli export onnx --model ibm-granite/granite-embedding-small-english-r2 --task feature-extraction <out>` and bundle the ONNX with the npm package (~50 MB increase). Simplest, deterministic versioning.
- **Option B** — publish the ONNX as a separate release asset; client downloads alongside corpus. Smaller npm but more moving parts.

**Decision.** Try `Xenova/granite-embedding-small-english-r2` first; if missing, use Option A. Plan task makes that decision after a one-line check.

**Parity test.** Pipeline-produced query embedding for a fixed string must match runtime-produced embedding within `1e-4` cosine distance. Test on every release; below threshold blocks release.

## 5. Testing strategy

### 5.1 Unit (per package, per source)

- `sources/legislation.py` — parse a recorded compilation XML fixture, assert chunk count + heading_path structure + effective dates.
- `sources/law_ato.py` — three fixtures: one TR, one PBR, one case summary. Assert doc_type tagging, effective_from extraction, anchor extraction.
- `sources/state_revenue/<juris>.py` — one fixture per jurisdiction. Assert tax-topic classification.
- `extractors/definitions.py` — pin against a known ITAA 1997 dictionary section, assert specific terms extracted (e.g. "trading stock" → s 70-10).
- `extractors/thresholds.py` — pin against a known value per threshold + per known historical date. E.g. `instant_asset_write_off` at `2024-06-30` must equal `20000`.
- `extractors/citations.py` — string-level regex tests covering "TR 2024/5", "s 8-1", "[2024] FCA 100", "Division 7A", etc.
- `manifest.py` — schema validation + round-trip.
- `update.ts` — mocked GitHub API, fake release with known sha256 + bad sha256, atomic rename verification.

### 5.2 Integration

- Build a 200-doc fixture corpus mixing all 4 new sources + the v0.1 ato.gov.au content. Run the full MCP test suite against it via the same `testToolBehaviour(adapter)` pattern from v0.1.
- Point-in-time integration: insert two chunks of "the same" Section 8-1 with non-overlapping date ranges, assert search with `pit=2020-01-01` returns the pre-amendment chunk and `pit=2024-01-01` returns the post-amendment chunk.
- `get_definition` integration: query "trading stock" — must return `kind: "statutory"` with ITAA citation. Query a clearly non-statutory term ("hostility") — must return `kind: "ordinary"` from WordNet fallback.
- `get_threshold` integration: 5-key smoke test against the seeded thresholds with explicit dates.

### 5.3 Eval (runs in release CI, blocks bad releases)

- 50-question hand-curated eval across topics (10 personal, 10 business, 10 super, 10 GST, 10 CGT/investment). Each Q has 1-3 expected `doc_id` citations.
- Metrics: `recall@10 ≥ 0.90`, `MRR ≥ 0.7`. Below threshold = release blocks.
- Eval set lives at `packages/pipeline/tests/eval/queries.jsonl`; CI runs it against the freshly built corpus.

### 5.4 Embedding parity (per-release)

- Generate query embedding for 5 fixed strings via Python pipeline.
- Generate query embedding for the same strings via Node `OnnxEmbedder`.
- Assert cosine distance `< 1e-4`. If above, release blocks.

### 5.5 Backwards-compat

- All v0.1 tests must still pass against a v0.2-built corpus.
- A v0.1 client (older MCP) connecting to a v0.2 corpus must still get usable results — schema is additive.

## 6. Open questions (deferred to the implementation plan)

1. **GitHub Actions runner time limit.** GH-hosted runners have 6-hour limits. ~150k-doc corpus build at current scrape rates is ~3.5 h crawl + ~1 h embed + ~30 min package = 5 h, uncomfortably close. Two fallbacks: (a) self-hosted Mac mini runner (William has Apple silicon, easy GPU acceleration too), (b) split build into per-source jobs that share a SQLite via artefact upload/download. Decide in plan week 1.
2. **Legislation XML schema drift.** `legislation.gov.au` has shipped XML in slightly different shapes over time. Pin against schema versions and handle multiple. Identify all schema variants in plan week 1.
3. **law.ato.gov.au sitemap availability.** Verify the sitemap URL actually exists and is complete. If not, paginated search-result crawling is the fallback. Test in plan week 1.
4. **PBR volume realism.** Claimed ~120k edited PBRs based on ato-mcp's count. Verify actual ATO-published count and estimated SQLite size impact before committing.
5. **Granite ONNX availability on `Xenova/`.** Already noted in §4.2. Check the HF Hub at plan-write time; either use the mirror or self-export.
6. **State revenue NAP/structure heterogeneity.** 8 jurisdictions, 8 site structures. Estimating per-jurisdiction scraper effort is hard without looking at each. Plan budgets ~1 day per jurisdiction with parallelism between them.
7. **WordNet license acceptance.** Open English WordNet 2024 is CC-BY 4.0. Attribution must appear in the bundled README and the tool output's footer. Mechanically simple but must not be forgotten.
8. **PIT default for the agent.** Current plan: `pit` defaults to today. For "tax return for FY24" questions, the agent should pass `pit=2024-06-30` explicitly. Document this in the MCP `initialize` instructions surfaced to clients.

## 7. Phased delivery within v0.2

The single v0.2 spec is large, so the implementation plan phases its execution. Sketch only — the writing-plans skill produces the detailed plan.
