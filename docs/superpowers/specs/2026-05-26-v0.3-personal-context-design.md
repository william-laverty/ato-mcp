# ato-pro v0.3 — personal context + hosted mode

**Date:** 2026-05-26
**Status:** Approved for implementation planning
**Owner:** William Laverty
**Builds on:** [v0.1 scaffolding spec](2026-05-25-ato-pro-mcp-design.md) and [v0.2 wider-corpus spec](2026-05-25-v0.2-wider-corpus-design.md), both shipped on `main`. v0.2 corpus = 29,180 docs / 224,585 chunks installed.

## 1. Goals, non-goals, success criteria

### Goals

1. **Personalisation layer** — every agent conversation knows the user (state, residency, business structure, ABN, GST status, industry, occupation, dependants, super fund type, investment property/shares/crypto holdings) without re-asking each session. The agent calls `get_user_facts` once on `initialize` and reasons accordingly.
2. **Web onboarding** at `ato-mcp.com` — polished multi-step facts wizard, magic-link sign-in, ABN checksum, ANZSIC industry picker, disclaimer gate. Open-source so users can verify what's collected.
3. **Deployment-choice flow** — user picks Local or Hosted at the end of onboarding. Each comes with plain-English tradeoffs. Both end in a single command/snippet the user pastes into Claude Code.
4. **Hosted backend** at `api.ato-mcp.com` — Vercel functions over Supabase Postgres + pgvector + Postgres FTS, bearer-token auth, the same TypeScript tool implementations as the local MCP (shared core), per-user rate-limit.
5. **Shared tool core** — refactor `packages/mcp/src/tools/` into `packages/shared/src/tools/` so the 8 existing tools plus v0.4 workflow tools land in both runtimes without duplication.
6. **Granite Small R2 embedding swap** — same model on pipeline, local MCP, and Vercel function. Corpus re-embeds in this phase.
7. **Anonymous-aggregate analytics** — `users`, `user_facts`, `usage_events` tables in Supabase. No tool name in usage events. No query text. No results. RLS verified by integration test on every CI.

### Non-goals (v0.3)

- Hero workflow tools (`deduction_discovery`, `bas_prep_checklist`, etc.) — v0.4.
- Edited PBR ingest, state revenue, citation graph extraction, WordNet fallback — already deferred from v0.2, still deferred.
- Multi-tenant / team / agent-portfolio features. Each user is their own.
- Payment processing or paid tiers. Hosted is free in v0.3.
- Mobile-native apps. Web onboarding is responsive; everything else is agent-driven.
- AI-generated tax advice in the MCP's voice. The MCP returns retrieval + facts; the agent does the prose.
- Federated identity (Google / GitHub OAuth). Magic-link email only.
- Multi-language UI. English / AU only.
- Self-host instructions for the hosted backend.

### Success criteria (measurable)

- New user can complete onboarding and have a working MCP in < 10 minutes (including downloads).
- `get_user_facts` returns within 50 ms (local) or < 200 ms p95 (hosted).
- A v0.2 local-MCP install continues working — `update <path>` and the v0.2 tools unaffected.
- RLS isolation test passes: user A cannot read user B's facts or usage events via any endpoint.
- Hosted backend handles ≥ 10 concurrent users without timeout.
- Privacy policy mirrors the actual schema and event types literally — auditable claim.
- All v0.2 tests still green after the shared-core refactor.

## 2. Personal facts model, storage, `get_user_facts`

### 2.1 Facts schema (the 25 fields)

Locked from v0.1 spec §5. Defined once in `packages/shared/src/facts.ts` (zod) and mirrored in Supabase as a typed Postgres row.

```ts
export const UserFactsSchema = z.object({
  given_name: z.string().min(1),
  state: z.enum(["NSW","VIC","QLD","WA","SA","TAS","ACT","NT"]),
  residency_status: z.enum(["resident","non_resident","temporary_resident","working_holiday_maker"]),

  has_abn: z.boolean(),
  abn: z.string().regex(/^\d{11}$/).optional(),
  business_structure: z.enum(["sole_trader","partnership","company","trust","none"]),
  business_name: z.string().optional(),
  industry_code: z.string().optional(),
  occupation: z.string().optional(),
  gst_registered: z.boolean(),
  gst_period: z.enum(["monthly","quarterly","annual","n/a"]),
  payg_instalments: z.boolean(),
  fbt_payer: z.boolean(),

  has_spouse: z.boolean(),
  dependants: z.number().int().min(0).max(20),
  hecs_help_debt: z.boolean(),
  private_health_insurance: z.boolean(),
  has_investment_property: z.boolean(),
  has_shares_or_managed_funds: z.boolean(),
  has_crypto: z.boolean(),
  super_fund_type: z.enum(["industry","retail","smsf","unsure","none"]),

  current_fy: z.string().regex(/^\d{4}-\d{2}$/),
  prior_fy_lodged: z.boolean(),

  accepted_disclaimer_at: z.string(),
  facts_updated_at: z.string(),
  schema_version: z.literal(1),
});
```

**Validation rules** beyond zod:
- ABN checksum (modulus 89) — validated client- and server-side
- `gst_period` must be `n/a` iff `gst_registered === false`
- ANZSIC code must match a known 4-digit class (bundled list)
- `current_fy` must be a valid AU FY identifier (e.g. `2025-26`)

### 2.2 Storage

**Local mode** — facts live in `~/.ato-pro/config.json`:

```json
{
  "mode": "local",
  "user_id": "u_abc123",
  "facts": { ...UserFacts },
  "facts_etag": "2026-05-26T03:00:00Z",
  "analytics_token": "..."
}
```

`facts_etag` reflects when the user last saved via web app. The MCP doesn't sync at runtime — facts are downloaded once at onboarding completion and stay until re-onboard or `ato-pro-mcp facts pull`.

**Hosted mode** — facts live in Supabase `user_facts` table (canonical). `~/.ato-pro/config.json` holds only the bearer token + user_id + mode:

```json
{
  "mode": "hosted",
  "user_id": "u_abc123",
  "api_endpoint": "https://api.ato-mcp.com",
  "bearer_token": "atompro_v1_..."
}
```

MCP fetches facts on `initialize` and caches in-process for the session.

**Supabase schema**:

```sql
CREATE TABLE users (
  user_id        TEXT PRIMARY KEY,
  email          TEXT UNIQUE NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_seen_at   TIMESTAMPTZ,
  mode           TEXT NOT NULL CHECK (mode IN ('local','hosted')),
  schema_version SMALLINT NOT NULL DEFAULT 1
);

CREATE TABLE user_facts (
  user_id    TEXT PRIMARY KEY REFERENCES users(user_id) ON DELETE CASCADE,
  facts      JSONB NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE bearer_tokens (
  token_hash   BYTEA PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_used_at TIMESTAMPTZ,
  revoked_at   TIMESTAMPTZ
);

CREATE TABLE usage_events (
  id         BIGSERIAL PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
  event_time TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  event_type TEXT NOT NULL CHECK (event_type IN ('mcp_started','heartbeat','update_check','update_applied','facts_pulled')),
  mode       TEXT NOT NULL CHECK (mode IN ('local','hosted'))
);

-- RLS:
-- users:        user can SELECT their own row only
-- user_facts:   user can SELECT/UPDATE their own row only
-- bearer_tokens: never readable by client role; service role only
-- usage_events: user can SELECT their own rows; INSERT via service role
```

Bearer tokens: only `sha256(token)` lives in `bearer_tokens`. Plaintext shown once at issuance and stored in the user's config. Auth: `bearer_tokens.token_hash = sha256(presented) AND revoked_at IS NULL`.

### 2.3 `get_user_facts` MCP tool

```ts
// input — no args
{}

// output
{
  facts: UserFacts,
  mode: "local" | "hosted",
  fetched_from: "config_file" | "hosted_api"
}
```

Local mode: synchronous read from `~/.ato-pro/config.json`. Hosted mode: `GET https://api.ato-mcp.com/v1/facts` with bearer; cached in-process for the MCP lifetime.

**No `pit` param.** Facts describe current you, not historical you. State change → re-onboard or edit via web app.

### 2.4 New CLI subcommands

- `ato-pro-mcp onboard` — opens `https://ato-mcp.com/onboard?cli=<code>`, polls for completion, writes the config file.
- `ato-pro-mcp facts pull` — local mode: refresh facts from the web app's saved version.
- `ato-pro-mcp facts show` — print current facts (debugging).
- `ato-pro-mcp logout` — wipe config, revoke token if hosted.

## 3. Web onboarding and auth flow

### 3.1 Stack and structure

- **Domains:** `ato-mcp.com` (public site + onboarding), `api.ato-mcp.com` (hosted backend)
- **Framework:** Next.js 15 (App Router), TypeScript, deployed to Vercel
- **Styling:** Tailwind CSS
- **Auth:** Supabase Auth — magic-link email, 1-hour TTL, one-time use
- **Forms:** React Hook Form + zod (`UserFactsSchema` from `packages/shared`)
- **State:** server actions for form submission

New monorepo workspace at `packages/web/`. Layout sketched in §3.2 of brainstorming (omitted here for brevity; see implementation plan).

### 3.2 Onboarding flow (5 steps)

1. **Landing + disclaimer + email.** Plain-English "not tax advice" with required checkbox. Email submits → Supabase magic-link.
2. **Verify magic link.** Server validates token, creates `users` row if new, redirects to wizard.
3. **Facts wizard.** Multi-step within a single page. Conditional fields. ABN checksum-validated. ANZSIC autocomplete bundled. Progress bar. On submit: insert into `user_facts`.
4. **Pick mode.** Two cards side-by-side, plain-English tradeoffs (Local: download, offline, private; Hosted: no download, fresh, server-side queries with no-log policy). Updates `users.mode`.
5. **Install snippet.** Mode-specific. Hosted shows the bearer token **once**. User pastes the MCP config snippet into Claude Code. Page polls `/api/poll?user_id=…` for the first `mcp_started` event → "✓ MCP detected."

### 3.3 Account dashboard

Logged-in `/account`:
- Email, mode (with switch button → re-runs steps 4–5)
- Facts summary (read-only) + "Edit facts" link
- Bearer token panel (hosted): "Active since X. Revoke and re-issue?"
- Usage summary (no per-tool data)
- "Delete my account" — confirmation page → cascading FK delete

### 3.4 Privacy + terms pages

- **`/privacy`** mirrors stored schema *literally*. Schema-↔-policy contract test fails CI on mismatch.
- **`/terms`** covers: not tax advice; users responsible for verifying with a registered tax agent; ATO content under ATO publication terms; license (MIT for code).

### 3.5 `ato-pro-mcp onboard` CLI command

Implementation:

1. Generate short-lived (~10 min) one-time code (6 alphanumeric).
2. Open browser to `https://ato-mcp.com/onboard?cli=<code>`.
3. Poll `https://api.ato-mcp.com/v1/onboard/poll?code=<code>` every 2 s.
4. Web flow completes and submits the code → server stores `{code → user_id, mode, bearer_token or facts_json}` for 10 min.
5. Poll returns the bundle. CLI writes `~/.ato-pro/config.json`. Done.

Manual copy-paste from step 5 of §3.2 still works.

## 4. Hosted backend, shared-core refactor, embedding swap

### 4.1 Shared-core refactor

Move tool implementations from `packages/mcp/src/tools/` into `packages/shared/src/tools/`. Tools depend on **interfaces**:

```ts
// packages/shared/src/store/types.ts
export interface Store {
  stats(): Promise<StatsResult>;
  keywordSearch(query: string, k: number, pit?: string): Promise<SearchHit[]>;
  vectorSearch(vector: Float32Array, k: number, pit?: string): Promise<SearchHit[]>;
  getChunks(chunkIds: string[], neighbours: number, pit?: string): Promise<SearchHit[]>;
  getDoc(docId: string): Promise<DocResult | null>;
  getDocAnchors(docId: string): Promise<AnchorGraph>;
  getDefinition(term: string, pit: string | null): Promise<DefinitionRow[]>;
  getThreshold(name: string, pit: string | null): Promise<ThresholdRow | null>;
  close(): void;
}

export interface Embedder {
  embed(text: string): Promise<Float32Array>;
  readonly name: string;
}
```

Three consumers:
- `packages/mcp/` — `SqliteStore` + `OnnxEmbedder` (local), `RemoteStore` (hosted-mode shim)
- `packages/backend/` (new) — `SupabaseStore` + `WasmEmbedder`
- `packages/web/` — types only

Existing 59 MCP tests carry over (now in shared).

### 4.2 `RemoteStore` adapter

When the local MCP is in hosted mode, it forwards each tool call to the backend:

```ts
export class RemoteStore implements Store {
  constructor(private endpoint: string, private token: string) {}
  // one method per Store method, posting to /v1/<method>
}
```

In practice the MCP in hosted mode is a thin shim: 8 endpoints to forward.

### 4.3 Vercel backend

New `packages/backend/` workspace:

```
packages/backend/
├── api/v1/
│   ├── search.ts, get_chunks.ts, fetch.ts, stats.ts,
│   ├── get_definition.ts, get_doc.ts, get_doc_anchors.ts, get_threshold.ts,
│   ├── get_user_facts.ts          # special: reads user_facts table
│   ├── facts.ts                   # PUT /v1/facts — update user_facts (web)
│   ├── onboard/poll.ts            # CLI polls here
│   ├── usage_event.ts             # analytics ping endpoint
│   └── _middleware.ts             # bearer auth + rate-limit
├── src/
│   ├── supabase-store.ts          # implements Store over Supabase
│   ├── wasm-embedder.ts           # implements Embedder via @xenova/transformers WASM
│   ├── auth.ts                    # bearer validation
│   ├── rate-limit.ts              # Vercel KV token bucket
│   └── log.ts                     # structured logger, path-only scoping
└── test/                          # per-handler integration tests
```

Each Vercel function: parse + validate input, call the shared tool, return JSON. Middleware: validate bearer, rate-limit, attach `user_id` to request context.

**Auth** (paraphrased):

```ts
const token = req.headers.get("authorization")?.slice("Bearer ".length);
if (!token) return 401;
const { user_id } = await sb.from("bearer_tokens").select("user_id")
  .eq("token_hash", sha256(token)).is("revoked_at", null).single();
if (!user_id) return 401;
if (await rateLimitExceeded(user_id, 60, "1m")) return 429;
req.context.user_id = user_id;
```

**Rate limit**: per-user, 60 req/min, Vercel KV-backed token bucket.

### 4.4 Supabase corpus storage

Corpus tables mirror the SQLite schema in Postgres:

```sql
CREATE TABLE docs (...);                 -- same shape as SQLite
CREATE TABLE chunks (
  ...
  embedding VECTOR(384) NOT NULL,
  tsv TSVECTOR GENERATED ALWAYS AS (to_tsvector('english', text)) STORED
);
CREATE INDEX chunks_embedding_idx ON chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 200);
CREATE INDEX chunks_tsv_idx ON chunks USING gin (tsv);
-- anchors, citations, definitions, thresholds: same as SQLite
-- corpus tables: public read by authenticated roles (no RLS)
```

Import via `packages/backend/scripts/import-corpus.ts` — reads from a built `ato.sqlite`, batched `INSERT … ON CONFLICT` into Postgres. Runs in monthly corpus-build CI workflow.

**Hybrid search SQL** (mirrors local sqlite-vec + FTS5; RRF fusion):

```sql
WITH vec AS (
  SELECT chunk_id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
  FROM chunks ORDER BY embedding <=> $1 LIMIT 30
),
kw AS (
  SELECT chunk_id, ROW_NUMBER() OVER (ORDER BY ts_rank(tsv, websearch_to_tsquery('english', $2)) DESC) AS rank
  FROM chunks WHERE tsv @@ websearch_to_tsquery('english', $2) LIMIT 30
)
SELECT c.chunk_id, d.title, d.url, d.doc_type, c.text, c.heading_path,
       COALESCE(1.0/(60+v.rank),0) + COALESCE(1.0/(60+k.rank),0) AS score
FROM chunks c JOIN docs d ON d.doc_id = c.doc_id
LEFT JOIN vec v USING (chunk_id) LEFT JOIN kw k USING (chunk_id)
WHERE v.chunk_id IS NOT NULL OR k.chunk_id IS NOT NULL
ORDER BY score DESC LIMIT $3;
```

### 4.5 Granite Embedding Small R2 swap

- **Pipeline**: change `embedding_model` to `ibm-granite/granite-embedding-small-english-r2`. Re-embed corpus (~5 min for current 224k chunks).
- **Local MCP**: `OnnxEmbedder.load()` tries `Xenova/granite-embedding-small-english-r2` first; falls back to a bundled ONNX export if the Xenova mirror is missing (decision in plan week 1).
- **Hosted**: same model in Vercel via `@xenova/transformers` WASM. Cold start ~1 s; warm ~80 ms.

**Parity test in CI** — pipeline / local / backend embeddings for 5 fixed strings must match within `1e-4` cosine distance.

### 4.6 Hosted-mode embedding strategy

Vercel `/v1/search`:
1. Validate bearer + rate-limit (middleware)
2. Receive query text
3. `WasmEmbedder.embed(query)` inside the lambda
4. Hybrid SQL against Supabase
5. Return chunks

Query text **does** reach Vercel in cleartext over TLS. Privacy promise is "no log, no retention" — verified by open-source backend code. Not cryptographic privacy.

### 4.7 Migration for v0.2 users

1. `ato-pro-mcp update` detects embedding-model mismatch in `installed_manifest.json`.
2. Refuses to start; prints clear instruction.
3. `ato-pro-mcp update --force` fetches v0.3 corpus, atomic-renames. No data loss; old corpus replaced.

## 5. Testing strategy

### 5.1 Unit

- `packages/shared/tools/` — every tool tested with mock `Store` + mock `Embedder`. These tests are the contract; both `SqliteStore` and `SupabaseStore` must satisfy them.
- `packages/shared/facts.ts` — ABN checksum, ANZSIC, FY format, conditional `gst_period`.
- `packages/mcp/store/remote.ts` — mocked `fetch` for every method.
- `packages/backend/src/wasm-embedder.ts` — bit-identical to the pipeline's Python embedder on 5 fixed strings.
- `packages/backend/src/auth.ts` — token-hash compare, revoked tokens rejected, rate-limit math.
- `packages/web/` — `FactsWizard` form tests; Playwright happy path with mocked Supabase Auth.

### 5.2 Integration

- `testToolBehaviour(adapter)` runs twice: once with `SqliteStore` (seeded SQLite), once with `SupabaseStore` (Docker Postgres + pgvector).
- MCP in `mode=hosted`: asserts every tool call forwards correctly to a mock backend.
- Onboarding e2e: Playwright, mocked auth, fills wizard, picks local mode, asserts config file written.

### 5.3 RLS verification (security-critical, every CI)

- As user A's bearer: read user B's facts via `/v1/get_user_facts` → expect 200 returning *A's* facts, not B's.
- As user A direct Supabase: read user B's `usage_events` → expect zero rows.
- As user A: update user B's facts → expect 403.
- Unauthenticated: every `/v1/*` → 401.

Only test that protects the privacy promise. Failures block release.

### 5.4 Schema↔privacy-policy contract

Test parses `/privacy` markdown, extracts documented schema + event types, diffs against zod schema. Mismatch fails CI.

### 5.5 Eval

Same 50-question set from v0.2 §5.3. Runs against both SQLite (local) and Supabase (hosted) corpora. `recall@10 ≥ 0.90` blocks release. Granite swap expected to improve eval; drop blocks the swap.

### 5.6 Embedding parity (per-release)

5 fixed strings, pipeline / local-runtime / backend-runtime. All three within `1e-4` cosine distance. Blocks on mismatch.

### 5.7 Backwards compat

v0.2 client connecting to v0.3 hosted backend works for the tools that existed. `get_user_facts` from a v0.2 client returns `unsupported_tool`.

## 6. Open questions (resolved during the plan)

1. **`Xenova/granite-embedding-small-english-r2` availability.** Probe in plan week 1. Missing → bundle our own ONNX export via `optimum-cli`.
2. **Vercel cold-start cost of WASM model.** Could be 1–3 s. Measure in week 1; if unacceptable, move embedding to a dedicated Cloudflare Workers AI endpoint or Modal sidecar.
3. **Supabase pgvector index parameters.** `ivfflat lists = 200` is a starting guess for ~250k chunks. Tune with a recall benchmark.
4. **Bearer-token format.** Proposed: `atompro_v1_<32-byte base32>`. Lock URL-safe length and prefix.
5. **Magic-link domain.** Dev = Supabase default; prod = `auth.ato-mcp.com`. CNAME setup in plan.
6. **Hosted analytics retention.** Default: 90 days raw, then aggregate to monthly counts and drop row-level data.
7. **`ATO_PRO_USER_ID` env var visibility.** Acceptable (user IDs are opaque) but flag in docs.
8. **Multi-device support.** Default: each device gets its own bearer token; both work; account dashboard shows both.
9. **Domain config.** `ATO_PRO_WEB_URL` and `ATO_PRO_API_ENDPOINT` env vars with defaults — test/dev/prod environments differ cleanly.

## 7. Phased delivery within v0.3

- **v0.3-a** (refactor) — shared-core refactor. Move tools to `packages/shared/`. Introduce interfaces. All v0.2 tests pass. No new behaviour. Releases as `v0.3.0`.
- **v0.3-b** (Granite + facts schema) — embedding swap, corpus rebuild, `UserFactsSchema`, `get_user_facts` reads from `~/.ato-pro/config.json`, CLI subcommands. Releases as `v0.3.1`.
- **v0.3-c** (web onboarding) — Next.js app, Supabase Auth, facts wizard. Onboarding writes `~/.ato-pro/config.json`. Releases as `v0.3.2`.
- **v0.3-d** (hosted backend) — Vercel functions, bearer auth, `SupabaseStore`, corpus import. `mode=hosted` functional. Releases as `v0.3.3`.
- **v0.3-e** (analytics + privacy polish) — `usage_events`, RLS, schema↔privacy contract test, account dashboard, "delete my data". `v0.3.4` is the first release suitable for a public soft-launch.

Each phase ships independent value.
